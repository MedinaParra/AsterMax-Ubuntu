# AsterMax Mechanical C10.82 — STEP/VTK performance baseline

## Scope
This baseline is intentionally evidence-gated. It does not claim speedups. It preserves Windows x64, the native GUI, and native Windows Code_Aster as the only solver.

## Starting point
C10.82 branches from C10.81 (`dc7b43270c8c8ea17f42b27c044ccc75bc0736e0`). C10.81 instruments effective deferred ElementEdges materialization, including highlight paths, without changing edge/render behavior.

## Dynamic counters required before the next optimization
Capture one complete large-STEP import session with performance tracing enabled and retain the raw trace. At minimum record:

- render requests
- renders queued
- invalidations/renders executed
- actor additions / geometry actor additions
- deferred ElementEdges actors
- effective ElementEdges materializations
- highlight-triggered ElementEdges materializations
- camera/ResetCamera requests and effective camera work where currently instrumented
- tree rebuild/update events where currently instrumented

Do not report FPS, elapsed-time improvement, percentage speedup, or memory improvement unless the corresponding measurement was actually captured.

## Decision gates
1. If render requests are much greater than executed invalidations, preserve coalescing and inspect callers before changing scheduling.
2. If executed invalidations remain repeated during one import transaction, identify and remove only the redundant call path proven by the trace.
3. If deferred edges are materialized during import without a user-visible edge/highlight requirement, isolate that call path before changing behavior.
4. If camera work occurs repeatedly inside the import batch, move only the demonstrated redundant camera work to the finalization boundary.
5. If actor creation is repeated for the same imported object, inspect identity/cache ownership before adding caching.
6. Tree optimization requires evidence that tree rebuild/update work is repeated for the same import transaction.

## Next safe increment
The next code optimization must be selected from a captured trace, not from static call counts alone. Until such a trace exists, changes should be limited to instrumentation, reproducible harnesses, contracts, or fixes whose incorrectness can be demonstrated independently of timing.
